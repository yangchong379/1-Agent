# 05 实现复盘与下一步

本文件由 AI 根据本轮实际实现整理，不代替候选人的个人学习陈述。候选人独立复盘及用时待其实际操作后补记。

## 最难的问题

最难的是把“模型建议”“用户批准”和“保存成功”分开。若让模型输出最终 JSON 并自行声称 confirmed/saved，即使工具失败也可能给出成功文本。本实现将最终结果投影到经过校验的工具状态：确认由用户输入计算；保存由事务提交回执证明；原要求一直保留；模型只能决定下一步工具。

另一个难点是重复提交与确认更新同时存在。仅按请求 ID 去重会让不同 ID 的同一素材产生多份草稿；将整个请求永久缓存又无法对同一草稿应用后续批准。本实现使用请求内容绑定防止 ID 复用，并以素材/渠道唯一约束管理一份活动草稿，使精确批准能更新原 ID。不同原要求的修改仍需进一步设计专门流程。

## 实际修正和收获

1. 官方协议校验发现 DeepSeek 思考模式与 `tool_choice=required` 不兼容，改用 `auto`，并保留原工具调用 ID 及必要思考字段在内存回传。仅仅“兼容 OpenAI 协议”不足以证明某个服务可直接运行；真实接口验证仍待完成。
2. 新增查询后占用变化测试，证明保存必须重新查询冲突；只在模型查时段时验证一次会存在竞态。
3. 新增批准更新失败测试，确认事务回滚保留旧的待确认草稿，不能误报用户批准已保存。
4. 把循环结束、草稿保存、待确认和已发布拆成可核查字段，避免单一 success 布尔值掩盖业务状态。
