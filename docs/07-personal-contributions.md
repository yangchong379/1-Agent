# 07 个人贡献与协作过程

本项目采用AI辅助开发。我主要承担需求与验收推进、本机模型接入、真实评估执行、失败反馈与修复后复测，以及仓库交付协作；代码设计、具体实现、自动化测试和材料整理由AI协助完成。以下按本轮实际操作与运行证据说明我的贡献。

## 我的主要贡献

### 1. 提供业务目标和验收依据，持续核对关键边界

我提供了素材审核与发布排期题目及完整交付规范，围绕冲突调整、确认边界、防重复、越权发布和虚报保存成功逐项追问，并核对这些要求在方案和测试中的处理方式。

我重点关注的业务含义是：18:00被占用后，19:00是建议时间；草稿保存成功、用户已确认和实际发布是三个不同状态。我也对照考核要求核查了至少三组输入/输出/运行记录、六项验收覆盖和评估文档引用，进一步提出补跑真实模型记录。

相关材料：[需求与验收映射](01-requirements.md)、[方案与业务约束](02-solution.md)、[实际评估](03-evaluation.md)。

### 2. 完成真实模型的本机接入操作

我提供了DeepSeek官方平台信息，在Windows本机执行接入命令、通过密码窗口输入接口密钥，并反馈PowerShell命令输入和隐藏输入遇到的实际问题。AI据此调整了连接入口，我再次操作并成功跑通真实模型冲突案例。

这一步把项目从可离线演示的流程推进到真实模型调用。密钥由我在本机输入，仓库保存的是输入样例、模型工具决策和业务结果。

相关材料：[连接脚本](../scripts/connect_deepseek.py)、[首次真实冲突Trace](../examples/runs/live-conflict.json)。

### 3. 执行完整真实评估，提供失败反馈

我运行了13组真实模型场景，并把终端中的失败结果反馈给AI。首轮结果为8/13通过，暴露了模型工具调用格式、重复提交准备过程和批量场景处理方面的问题。

我的贡献是提供真实执行环境、运行操作和可复现的失败现象；源码级定位、修复和自动化回归由AI协助完成。问题没有停留在“离线测试通过”，而是进入了真实接口验证和修复闭环。

相关材料：[首轮真实结果](../examples/runs/live/REPORT.md)、[首轮失败复核](../examples/runs/live/REVIEW.md)。

### 4. 完成修复后的针对性复测

代码修复后，我重新运行失败项入口，完成conflict、save_failure、duplicate、changed_occupancy和batch五项真实复测，结果为5/5通过。

复测记录验证了替代时段待确认、保存失败如实返回、重复请求复用原草稿，以及批量素材分配不同时间等行为。首轮失败和重跑分别保留，结果表述为“首轮8/13、修复后失败项5/5”，没有将两轮合并成一次全量成功率。

相关材料：[失败项重跑结果](../examples/runs/live-retry-1/REPORT.md)、[跨版本对照](../examples/runs/LIVE-REVIEW.md)。

### 5. 推进GitHub项目交付

我创建并提供了GitHub目标仓库，完成账户登录授权，明确要求上传代码、文档、测试与运行记录。AI执行Git提交、推送、远端重新克隆和文件校验，形成可以访问和复现的仓库交付。

相关材料：[提交入口](../SUBMISSION.md)、[运行指南](../README.md)。

## 我在本次实践中重点学习和核对的内容

- Agent的模型负责选择动作和参数，工具与数据库负责执行约束；需要通过实际观察和下一步动作证明决策循环。
- 业务工具采用合成数据不影响验证模型调用过程；模型自身被Mock替代时，只能说明流程可运行。
- 正向场景通过不足以覆盖业务风险，还需要缺资料、冲突、工具故障、重复提交及确认边界的记录。
- 复测应保留首轮失败并标明版本，不能把修复后结果写回原始失败日志。
